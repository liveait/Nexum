# Changelog

All notable changes to Nexum will be documented here.

## Unreleased

### Added

- **Core**: task lifecycle, scheduler, resolver integration, and event collection. SQLite storage and restart recovery now support the running server; recovery persists the normalized `Queued` state of previously downloading, paused, or retrying tasks.
- **Engine**: in-memory and HTTP adapters. The HTTP adapter follows redirects, stages the response in a `.part` file, renames a complete download into place, reports progress after each written response chunk, and exposes cooperative pause/cancel control for server workers. The server-owned path now keeps a stable hidden partial file and atomic JSON sidecar, and resumes only a validator-matched `206 Partial Content` response after restart. The generic synchronous adapter remains without pause/resume capability.
- **Protocol**: JSON-RPC 2.0 task and server-info methods, a version identifier, credential fields, event envelope/buffer types, and `events.event` notifications for subscribed clients. `TaskView`, returned by `task.get` and `task.list`, includes persisted progress and an `error` field for the most recent transfer error. The protocol defines `-32001` for authentication failures; the server validates configured Bearer or ApiKey credentials before RPC dispatch and event subscription.
- **Server**: localhost, line-delimited TCP JSON-RPC with one thread per connection. It holds a data-directory lock, stores tasks in `data_dir/nexum.sqlite`, recovers them before listening, and fails startup on directory, lock, database, or recovery errors. Queueing an HTTP/HTTPS task, recovering queued work at startup, and completing or failing an active HTTP transfer trigger the server's automatic dispatcher. It claims eligible tasks up to the scheduler concurrency limit while skipping unsupported sources and overlapping destinations. `task.start` remains a manual kick that launches one HTTP/HTTPS worker and returns before transfer completion, then uses the same dispatcher to fill other slots. The server persists progress when a response has added 1 MiB or 250 ms have elapsed, then flushes the final snapshot before persisting `Completed`. Failures preserve the error in `TaskView` and requeue while the default three-retry budget remains; the dispatcher starts the retry when a slot is available, and after the budget is exhausted the task stays `Failed`. A new claim clears the previous error. Active HTTP workers now support chunk-boundary `task.pause`, same-process `task.resume`, and destructive `task.remove` cancellation; a blocking response read can delay pause until the 30-minute HTTP timeout, while remove waits up to 30 seconds before returning an error. Restart recovery resumes a validator-matched HTTP partial with `Range`/`If-Range`; missing or changed validators, a `200` response, invalid `Content-Range`, inconsistent length, or a response without a validator fall back to byte zero. Clients can use a dedicated `events.subscribe` TCP connection for sequenced task and scheduler notifications; the stream has no replay buffer, so clients refresh a full snapshot after connecting or reconnecting. The configured `max_connections` limit is enforced at TCP admission; excess connections are closed immediately. When `require_auth` is enabled, the server requires a matching `auth_scheme` and non-empty `auth_token` before every RPC and `events.subscribe`; missing or invalid credentials return `-32001` (`authentication required`). `server.auth` reports the active scheme without exposing the token, and incomplete authentication configuration stops startup.
- **CLI**: task commands, a reusable TCP JSON-RPC client, saved server address and plain-text credential fields, `auth set`/`auth clear` validation, server inspection, RPC error formatting, and a verified `tls://host:port` transport using system roots and hostname validation. Plaintext credentials are sent only to an actual loopback peer; TLS credentials are sent only after a successful handshake.
- **Desktop**: Tauri 2 + React task UI connected to the TCP server, with a server-address field, native destination picker, dedicated event subscription, per-connection sequence-gap detection, debounced task refresh, and polling fallback with full-snapshot resync after reconnects. On macOS, General settings save and clear per-Server Bearer/ApiKey credentials in Keychain. The secret is not returned to React; Tauri attaches it to ordinary RPC and `events.subscribe`. Saving, clearing, or changing the active Server restarts the event stream and refreshes the task snapshot. Plaintext credentials remain restricted to loopback addresses; verified TLS addresses use transport-scoped Keychain accounts. Other platforms retain unauthenticated Desktop connections but do not support credential save or clear. Tauri JavaScript and Rust versions are pinned to compatible minor releases, and the macOS bundle identifier no longer ends in `.app`.
- **Desktop accessibility**: `⌘N` opens Add Download and `⌘F` focuses Downloads search; Escape closes either surface. Task selection supports Enter/Space, Up/Down, and Home/End. The Add sheet traps Tab focus and restores focus on close, while task controls and Inspector progress expose accessible names and status. Desktop transitions and indeterminate progress animation honor reduced-motion preferences. System appearance, localized UI strings, and native task context menus remain planned.
- **Browser**: Manifest V3 context menu, link detection, and popup configuration. The extension sends `task.create` and `task.queue` through the server's HTTP or HTTPS `POST /jsonrpc` bridge based on the saved address; bare `host:port` remains HTTP, while `tls://host:port` maps to browser HTTPS with normal certificate validation and no HTTP downgrade. JSON requests from validated extension origins receive CORS headers while web-page origins are rejected, event subscriptions remain TCP-only, and credential settings are not yet available.
- **Security**: credential, TLS, and rate-limit types. The server enforces configured Bearer/ApiKey authentication and optional process-wide RPC rate limiting with one token bucket shared by TCP and HTTP `/jsonrpc`. Limiting is disabled by default; complete, valid rate and burst settings are required to enable it. Parsed, authenticated requests, including `events.subscribe`, consume tokens; authentication failures, event heartbeats, and HTTP `OPTIONS` preflight do not. Excess calls with an `id` receive JSON-RPC `-32002` (HTTP status `200`); notifications without an `id` are dropped without a JSON-RPC response. Invalid or incomplete rate-limit settings and unreadable files explicitly passed with `--config` stop startup. The server now accepts paired PEM certificate and private-key paths for TLS across TCP JSON-RPC, event subscriptions, and HTTP `/jsonrpc`; the CLI and Desktop verify `tls://` server names with system roots, and Browser maps `tls://` to the browser's HTTPS trust path without downgrade.
- **Tests**: runtime-generated certificates cover successful TLS TCP/HTTPS requests, plaintext rejection, browser-extension CORS allow/reject behavior, configured TCP/HTTPS authentication, authenticated `events.subscribe`, Server startup rejection for incomplete or invalid certificate/key material, and handshake rejection for untrusted or wrong-hostname certificates. CLI tests verify that credentials are sent after a trusted handshake, never sent after trust or hostname failure, and never retried over plaintext; Desktop tests exercise the same credential gate for RPC and event subscriptions.
- **Plugin**: manifest, permission, capability, lifecycle-state, and provider-trait foundations. Core tracks plugin manifests but does not yet load provider engines or resolvers.
- **Media**: media and workflow models with simulated, in-memory probing and job execution; no real media processing is wired in.
