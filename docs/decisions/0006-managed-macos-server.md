# ADR 0006: App-Managed Local Server for macOS

- Status: Accepted for M1; Server managed bootstrap implemented, Desktop supervisor pending
- Date: 2026-10-10

## Context

The Desktop is currently a TCP JSON-RPC client. It defaults to `127.0.0.1:39100`, stores that address in `settings.json`, and needs a separately started Server. The Server defaults to `./data/nexum.sqlite` relative to its launch directory and locks that data directory. Its listener also carries the HTTP bridge and event stream. A loopback listener alone does not authenticate the Desktop: another local process can bind a fixed port before the Server or call its RPC methods. HTTP partial files and their validator sidecars live beside each destination under [ADR 0004](0004-cross-restart-http-resume.md).

M1 makes a macOS installation usable by opening the App and pasting an HTTP(S) URL. Nexum has not been released, so M1 does not need migration from earlier development builds or separately launched CLI Servers. Existing development data must not be deleted or silently attached.

## Decision

### Ownership, identity, and packaging

1. The Tauri Rust backend is the sole supervisor of one bundled `nexum-server` child for the App's **Managed** mode. The frontend requests task operations from backend commands; it never selects the managed RPC address or receives the managed credential. The App does not use a system service, a login item, a shell, or an executable found on `PATH`. The App bundles the matching architecture's Server executable and launches its resolved absolute bundle path directly. The App build embeds the Server binary's SHA-256 digest, which the backend checks before launch alongside its build and protocol versions; a missing, changed, or incompatible binary is a visible startup error, with no fallback to an installed Server. M3 adds distribution signing of the App and nested binary.
2. Managed mode is the default. **External** mode remains a separate Settings choice for a user-specified address, TLS behavior, and per-address Keychain credential. Switching modes never sends the managed token to an external address and never stops an external process. No compatibility or data migration path for pre-release Desktop settings is part of M1.
3. The App owns the child by retaining its OS process handle and private stdin/stdout pipes. Managed startup uses a dedicated Server flag, with a small framed control protocol on stdin and exactly one readiness response on stdout; diagnostics go to stderr. The parent sends shutdown over stdin, and parent death closes it so the child exits. The App does not adopt a listener merely because it occupies the expected address, reports a protocol version, or holds the data-directory lock. A second App process must activate the first instance or show a clear already-running error; it must not start a second managed Server against the same data directory. After a crash, a new App instance starts a new child only after the old process has exited and the data-directory lock is free.

### Endpoint and authentication

4. The managed child binds only `127.0.0.1` on an OS-assigned port (`port 0`); the fixed `39100` default remains for manually started external Servers. The child reports its actual bound address, process/build identity, and protocol version through its private stdout pipe, without the secret. The backend accepts readiness only from the process handle it spawned, verifies the version and an authenticated `server.version` probe, and gives up with a visible error after a bounded startup timeout. A port collision therefore cannot redirect the App to an unrelated Server; no blind fallback to `39100` or to a later free-port scan is allowed.
5. The backend generates a cryptographically random, per-launch Bearer secret and passes it over the child's private stdin pipe before the child binds, never as a command-line argument, environment variable, settings file, log, or WebView event. The child requires it for every JSON-RPC call, `events.subscribe`, and HTTP `/jsonrpc` request. Existing Server authentication can enforce this once the managed startup path accepts a pipe-delivered secret. The backend retains the secret in memory only and attaches it to managed RPC and event connections after confirming the loopback peer. The Server still binds to loopback; CORS is not an authentication boundary. Browser pairing, remote access, and sharing this secret with CLI or extensions are outside M1.
6. Managed backend commands use the supervisor's endpoint and credential rather than accepting a frontend-supplied `server` string. Existing RPC, event, and credential commands must be removed or gated by backend mode so the managed UI cannot address an arbitrary Server. They expose specific task actions instead of arbitrary RPC forwarding. The managed add-download path accepts an HTTP(S) URL, an editable suggested filename, and an optional directory selected through a native chooser; the backend/server validate the name, generate the task ID, and allocate a unique destination against existing tasks and partial-file paths without creating the final file. Any response metadata used for naming must be validated before allocation. The no-clobber engine commit still rejects a file created externally after allocation. External mode continues to use its explicit address and existing RPC contract.

### Storage and lifecycle

7. The managed database and lock live under the stable Tauri application data directory, in a dedicated `server/` subdirectory keyed to the unchanged App identifier `com.nexum.desktop`. They never live in the App bundle, current working directory, temporary directory, or download directory. The default save location is the user's macOS Downloads directory itself, resolved with the platform API; the App does not create a `Nexum` subdirectory. A missing or unwritable Downloads directory requires an actionable choice and does not silently fall back to application data. A user-selected default download directory is saved in App settings, and the user may select a different destination for an individual task; each task's destination is persisted as an absolute path. Name collisions never silently overwrite an existing file. The backend rejects path traversal and unsafe names; the Server continues to reject destinations in its data directory and symlink destinations.
8. The new managed data directory starts independently of `./data` used by manually launched CLI/development Servers. The App neither scans, imports, attaches to, nor deletes that separate data. Once managed mode creates tasks, relaunches and App upgrades keep using the same managed directory. Any future managed-database schema migration must be transactional and preserve a recoverable backup; an unsupported downgrade must fail visibly rather than rewrite data. App updates must preserve the identifier and data path. Task destinations remain absolute paths, and destination-side partial files and sidecars remain in place for validated resume.
9. Managed downloads run only while the App process is running in M1. Closing the last window keeps the App process and child running, with the usual macOS Dock/menu path to reopen the window; explicit Quit stops them. On normal quit or a switch to External mode, the supervisor asks its own child to shut down, waits a bounded interval, then terminates it if necessary; it never kills a process discovered by port or PID file alone. An unexpected child exit triggers bounded restart attempts with backoff, followed by an actionable error and manual retry rather than an endless crash loop. The recovered Server applies its existing task recovery and validator-checked HTTP resume. The App refreshes a full task snapshot after every child restart or event-stream gap. A forced stop may leave a destination-side partial and sidecar, but must not expose an incomplete destination as completed or damage a preexisting file. [ADR 0004](0004-cross-restart-http-resume.md) remains authoritative for `Range`/`If-Range` validation and atomic completion without replacing an existing destination.

## Consequences and implementation order

- Add a managed startup mode and private control/readiness protocol to the Server, plus a Tauri supervisor. Keep the existing CLI flags and manually started Server behavior compatible.
- Introduce an explicit Managed/External settings schema. Refactor Desktop commands and event subscriptions to resolve the active endpoint in Rust.
- Add a managed default-destination and task-creation command. Do not claim the M1 acceptance gate until these are usable from the release App.
- `port 0` requires reporting the actual bound port; the current Server log line prints the configured port and is insufficient. The current `--auth-token` flag exposes a secret in process arguments and must not be used for the managed child.

### First implementation slice: managed Server bootstrap

On October 11, 2026, the Server gained a dedicated `--managed` entry point that accepts only an explicit absolute `--data-dir` and an optional positive `--max-connections`. It rejects external configuration, fixed-port, TLS, and command-line authentication flags. The existing manually started Server path remains available. The Desktop does not call this entry point yet.

- `nexum_protocol::managed` defines private pipe frames: a four-byte big-endian length followed by JSON, capped at 4096 bytes per frame. The first stdin frame has `type=start`, control version `1`, the Server package version, RPC version, and a 32-byte Bearer secret encoded as 64 hexadecimal characters. The Server validates it before creating storage, opening the database, or listening; an incomplete startup frame fails after five seconds. Generating the random secret remains the future Desktop supervisor's responsibility.
- stdout carries exactly one readiness frame with the control/Server/RPC versions, child PID, and actual loopback endpoint from `listener.local_addr()`. It contains no secret. Diagnostics use stderr, and frame-parser errors do not echo input. The future Desktop still needs to verify the bundled binary's SHA-256 digest, validate readiness, and perform an authenticated health probe.
- After startup, `type=shutdown` with control version `1`, stdin EOF, or an invalid control frame ends the child. The listener checks its control channel every 25 ms. It does not wait for blocked RPC, event, or HTTP workers and does not remove/cancel tasks to clear partial files. Exit relies on existing transactional persistence and cross-restart recovery; it does not guarantee flushing every in-flight byte before exit. Shared Server state retains the data-directory lock until workers holding the database exit with the process.
- Isolated process tests cover ephemeral endpoints, TCP/HTTP/events authentication, invalid/timed-out startup, duplicate data-directory ownership, private readiness output, lock release after Shutdown/EOF, and stalled-transfer resume and destination protection. They use independent temporary directories and HTTP fixtures without adopting development Server data.

This slice does not bundle the Server, implement the App supervisor/settings modes, select the App data directory, or wire native UI. M1 remains unaccepted. The next slice connects the Tauri backend to this protocol.

## Acceptance and verification boundary

- In a fresh macOS account, the actual built `.app` starts its bundled Server and downloads a pasted HTTP(S) URL to a collision-safe default destination, without a terminal, Server address, manual task ID, or manual file path. Task state and completed bytes survive quit/relaunch and an App upgrade.
- Tests cover a missing/incompatible bundled Server executable, startup timeout, child exit/restart budget, duplicate App startup, an occupied fixed external port, and a process impersonating `39100`; none causes the App to attach to or stop the unrelated process. Managed RPC, HTTP bridge, and events reject missing/wrong credentials. The token does not appear in args, environment, logs, settings, or frontend payloads.
- Explicit External mode can connect to a separately launched Server with its configured credential. Switching modes preserves managed tasks and the external address; quitting Managed mode leaves an external Server running. Existing CLI/development `./data` remains untouched.
- Tests verify that App relaunch and upgrade reopen the same managed database. Crash/forced-stop tests verify that a preexisting destination is preserved and validated partial data resumes or safely restarts. They must also cover the gap between publishing a complete destination and persisting `Completed`, reconciling the task with the intact file instead of reporting a failed re-download.
- Native release-App checks cover clean launch, paste-to-download, quit/relaunch, abnormal child exit, upgrade, permissions failure, and actionable error presentation. Automated process/protocol tests do not substitute for this native check.

## Alternatives considered

- **Connect to `127.0.0.1:39100` if occupied:** cannot establish ownership or prevent a local process from impersonating the Server.
- **Run a persistent launch agent:** changes quit/background semantics and requires a separate installation/update/security lifecycle before the first usable App.
- **Reuse `./data` automatically:** its location depends on the launch directory and could select unrelated or active development data.
- **Pass the token by command-line flag or rely on loopback/CORS:** exposes the token or leaves local RPC unauthenticated.
